# YaaKanban Spec

Yet another agent kanban: a macOS menu-bar app that watches coding-agent sessions across harnesses and tells the user when a task finishes, gets stuck, or needs input. Goal: see cross-agent work at a glance and cut context-switching cost.

Decisions below were agreed with the user on 2026-10-20 (grilling session).

## 1. Scope

- Personal MVP, but agent integrations are installable/uninstallable modules (distribution-ready shape).
- Local machine only. No remote agents, no phone push, no loop detection, no free-text replies in MVP. The only network traffic is opt-in anonymous telemetry (§6).

## 2. Stack

- Swift / SwiftUI, SwiftPM, packaged into `.app` by `make app`. macOS 14+. Ad-hoc signing. Login item via `SMAppService`.
- No separate daemon in MVP: the app process owns the socket server. A small CLI `yaak` (bundled at `Contents/Helpers/yaak`) is what hooks call.

## 3. Integrations

- First batch: Claude Code, pi, Codex, OpenCode, Cursor. Second wave, in four batches: (1) Hermes, DeepSeek dsh; (2) Qwen Code, Factory Droid, Copilot CLI, Gemini CLI; (3) ZCode, Kiro CLI (V3 only), Kimi Code; (4) Cline, omp, Windsurf.
- Like Adrafinil: write entries into each agent's native hook/plugin location; idempotent install/uninstall; coexist with Adrafinil.
  - Claude Code: `~/.claude/settings.json` hooks.
  - Codex: `~/.codex/hooks.json` only (not `notify`, which is single-slot and already taken). Append only; the user must trust via `/hooks`.
  - Cursor: `~/.cursor/hooks.json`.
  - OpenCode: `~/.config/opencode/plugins/yaakanban.ts`.
  - pi: `~/.pi/agent/extensions/yaakanban.ts`.
  - Hermes: `hooks:` in `~/.hermes/config.yaml`, edited line by line; each item and each key we add carries `# yaakanban`.
  - DeepSeek dsh: through the official `@deepseek-ai/dsh-hooks-claude-code` bridge. `~/.dsh/yaakanban/` holds a Claude-shaped `hooks.json` and a local bundle the user adds per profile (`dsh plugin --profile <p> add file:<bundle>`).
  - Qwen Code: `~/.qwen/settings.json` hooks; PermissionRequest is answered from the app.
  - Factory Droid: `~/.factory/hooks.json` (or legacy `hooks/hooks.json`); an event only `settings.json` `hooks` defines gets ours there, since the hooks file would hide it.
  - Copilot CLI: `~/.copilot/hooks/yaak.json`, owned by YaaKanban; permissionRequest is answered from the app.
  - Gemini CLI: `~/.gemini/settings.json` hooks (timeouts in ms).
  - ZCode: `hooks.events` in `~/.zcode/cli/config.json`; `hooks.enabled` is switched on only when the user has not set it and no other hooks are there; PermissionRequest is answered from the app.
  - Kiro CLI: `~/.kiro/hooks/yaak.json`, owned by YaaKanban; V3 engine only.
  - Kimi Code: `[[hooks]]` tables in `~/.kimi-code/config.toml`, edited as text; its PermissionRequest is notify-only.
  - Cline: one executable script per event in `~/Documents/Cline/Hooks`, owned by YaaKanban; no permission hook.
  - omp: `~/.omp/agent/extensions/yaakanban.ts`; sub-agent sessions skipped; tool approvals shown as needs input.
  - Windsurf: `~/.codeium/windsurf/hooks.json` (Cascade actions); no session or permission events.
- Settings lists only detected agents (its config directory exists, or our hooks are installed); undetected ones are hidden (2026-10-24). `yaak install` skips them too. First run (2026-10-27): with no integration installed, the empty panel says no agent is connected and offers 连接 Agent…, which opens the setup guide (the menu has the same row); setup guide (2026-10-27): a window in two steps, opened by itself on a launch with nothing installed and the guide not yet done (users who already have integrations never see it unasked), reopened from the menu, the empty panel and Settings › General: (1) the detected agents, each row going Install → Installed (ticked by itself the next time the agent is used; no session or message is asked for) → Connected once a hook event from it arrives, with any approval steps (Codex: the desktop app's Settings → Hooks by default, the terminal's /hooks on a switch; revised 2026-10-27), rechecked whenever the user comes back to the app or one of its windows rather than polled (revised 2026-10-27; Settings likewise, so it has no Recheck button); each row's state is one capsule (已连接 / 等待首次使用 / 待授权), rows needing approval first, and Continue with any still unapproved asks first (Skip Setup does not) (2026-10-27), and a large Connect All Agents button while any agent is not installed; (2) notifications (the system prompt comes up on reaching this step, not at launch, while the guide is due; when denied the row says so and opens System Settings), then launch at login, Accessibility (optional; revised 2026-10-27: an Allow… button that brings up the system prompt there and then), linking `yaak` to `~/.local/bin` when missing, and statistics, all on by default and applied on Done; the user turns off what they don't want (a reopened guide shows the current settings, and a no to statistics given earlier stands; replaces the launch alert that time). While the guide is open the app shows in the Dock and the app switcher, and clicking its Dock icon brings the guide back (2026-10-27). Revised 2026-10-30: the main window keeps the app in the Dock and the app switcher too, while it is open; the Dock icon brings the guide back, else the main window. Clicking a notification goes to its session only, without opening the main window. Outside the guide, a card click that needs Accessibility (Wave tab, editor window) first says what it is for and that macOS will ask next, with Continue / Not Now; Not Now is remembered and the jump goes ahead without it (2026-10-27). The window is frameless (no title bar or traffic lights, its own close button, progress at the top right) and the page never scrolls: only the agent list does. Closing it any way counts as done and asks for notifications if not yet asked; a card whose agent is found but has no integration shows a plug mark (status approximate, no approvals or done alerts); a successful install says only sessions started afterwards report.
- Authorization: where an agent asks the user to approve hooks, status shows 待授权 with steps, Settings has 重新检查, and cards of that agent show a warning. Rechecked on launch, on demand and every 60 s. Exact checks: Codex (recompute the `/hooks` trust hash against `config.toml`), Hermes (`shell-hooks-allowlist.json` or auto-accept), dsh (a profile depends on the bundle), Qwen (`disableAllHooks`), Droid (`hooksDisabled`), Gemini (`hooksConfig.enabled` / `disabled`), ZCode (`hooks.enabled`, a hook of ours switched off), Kiro (`chat.agentEngine` is not v3). Folder-trust and similar caveats are shown as notes.
- Hook path: the app keeps `~/.local/share/yaakanban/bin/yaak` linked to its bundled `yaak`, and hooks call that link, so moving or updating the app does not change hook commands (or Codex trust hashes).
- Dry run masks values of secret-looking keys (token, key, password, auth…).
- Installer safety: back up every file before writing (`.yaak.bak`), `--dry-run` prints the change, tests use a temp HOME.
- Data: hooks drive state transitions; Claude session files (`~/.claude/sessions/<pid>.json`) backfill sessions without hooks and supply status.
- Transport: hook → `yaak hook <agent> <event>` → Unix socket JSON line → app. If the app is down, append to a spool dir; the app replays on start. Hooks return within ~100 ms and never block, except the bounded permission wait.

## 4. Model

- One row = one session. Turns (prompt → stop) are listed in detail. Sub-agents fold under the parent (“2 sub-agents running”); one whose parent is not on the board (2026-10-27; e.g. pi-subagents scouts of a pi session that never reported) gets no card of its own unless it needs input. Agents another agent runs as a tool (2026-10-26; e.g. Claude running `codex exec` through Bash) fold the same way under the calling session: the caller is a live top-level session whose agent process is an ancestor of the new one's (recorded by the hook; Cursor and Windsurf, whose hooks run in the editor hosting the terminal, never count as callers); one that needs input shows its caller card as needs input with its message. Revised 2026-10-30: while one still runs, a caller whose own turn ended shows as running, not 待验收, in the card, the counts and the menu-bar icon.
- States: `running`, `needs_input`, `stuck`, `idle`, `ended`.
- Stuck: running with no new event for 5 min; a single tool running > 5 min; process gone while still running. Running sub-agents count as activity. Thresholds configurable. Revised 2026-10-28: a tool the same agent has started another call after no longer counts as running for either rule (a Codex exec outliving its yield keeps running while the agent moves on; its end only comes when the agent polls it again); waiting tools still count.
- History fully kept in SQLite. Metadata (session, turn, tool name, summary) forever; full tool input/output 30 days.

## 6. Feedback & telemetry (2026-10-23)

- Distribution: website download and a Homebrew cask.
- Updates (2026-10-26): self-written, from GitHub Releases (`releases/latest`, no drafts or prereleases). The app checks at launch and every 6 h (Settings › Updates, on by default; off for builds not signed by the release team), downloads a newer zip in the background and installs only a bundle with the same id, that version and the same signing team. No alerts: one dismissible line on the floating panel offers to restart into it (also in the menu and settings); after an update the line says it is up to date and links to the release notes. Notes come from `CHANGELOG.md`, published per release by `make release`.
- Feedback: menu and settings 反馈… open a prefilled GitHub issue (bug or feature form) with a diagnostics block the user sees first and can leave out. `yaak doctor` prints the same report. Diagnostics: versions, macOS, arch, per-agent integration status, app listening, spool size, database size, telemetry on/off; no paths, never session content.
- Telemetry: opt-in, off by default; asked once (first launch of a build with an Aptabase App Key). Off whenever `DO_NOT_TRACK` is set (in the app's or `yaak`'s environment). Only the app sends, never `yaak` or hooks. A random install id (resettable in settings) is kept so retention can be counted.
- What is sent: one JSON report per local day the app ran, sent after that day ends (at most the last 7 days, a failed send is dropped, never retried). Contents: schema version, install id, day, app version, macOS major, arch, locale, integration status per agent, a fixed set of setting flags, feature counters from a fixed list (opening the panel, jumps by terminal kind, resume, approvals, rename, pin, feedback, installs), and, all in coarse buckets, those counters and the day's figures (sessions and turns per agent, agent hours, parallel peak, leverage). Never prompts, tool input/output, paths, project or session names, titles or tokens.
- Transparency: settings shows the exact next report; `yaak telemetry status|on|off`; field list in `docs/telemetry.md`.
- Backend: Aptabase, US region (EU at first, changed by the user 2026-10-23; hosted; revised 2026-10-23 from a self-hosted Worker, to avoid running a server; revised again 2026-10-23 from TelemetryDeck, whose free plan shows data up to a day late). Each report is one event `daily` with the fields as string props; the install id is sent only as its SHA-256 (prop `install`); Aptabase derives and stores country and region from the IP but not the IP. The App Key is set in `Info.plist` (`YaakAptabaseAppKey`); empty means telemetry is unavailable. Debug builds send as Aptabase debug data.
